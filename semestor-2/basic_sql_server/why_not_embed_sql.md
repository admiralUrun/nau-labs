# 🚫 Чому не можна писати SQL-запити безпосередньо в застосунку

## 🔐 1. Безпека: SQL-інʼєкції

При вставці SQL-запитів напряму в код, особливо з динамічними параметрами (наприклад, через `input()`), програма стає вразливою до **SQL-інʼєкцій**.

**Приклад атаки:**

```python
# Небезпечний приклад
query = "SELECT * FROM users WHERE name = '" + username + "'"
```

**Хакер вводить:**
```
' OR '1'='1
```

👉 Запит стає:
```sql
SELECT * FROM users WHERE name = '' OR '1'='1'
```

Це дозволяє обійти автентифікацію або отримати доступ до всієї таблиці.

---

## 🔁 2. Погана підтримуваність коду

Коли SQL-запити захардкожено в коді:
- їх важко оновлювати
- вони повторюються в кількох місцях
- логіку важко тестувати й розділяти

---

## 🧱 3. Відсутність шарів абстракції

Писати SQL прямо в інтерфейсі — це порушення архітектурного принципу **розділення відповідальностей**:

- UI має показувати дані
- База має зберігати дані
- Логіка програми має бути посередником

---

## 🐞 4. Важче налагоджувати

При зміні структури бази (наприклад, нова колонка) доведеться шукати всі місця в коді, де є запити — це важко підтримувати.

---

## ✅ Як правильно

- Використовувати **параметризовані запити**:
```python
cursor.execute("SELECT * FROM users WHERE name = %s", (username,))
```

- Винести SQL у окремий **шар або файл**
- Використовувати **ORM (SQLAlchemy, Django ORM)** якщо проєкт великий
- Додавати валідацію даних до взаємодії з БД

---

## 💡 Висновок

> Писати SQL прямо в інтерфейсі — це як паяти проводи навколо розетки, а не через вилку: може і працює, але рано чи пізно буде 🔥.

Розділяй логіку, UI та доступ до даних.
